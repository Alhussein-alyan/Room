part 1 - what is information retrieval

definition

information retrieval (ir) means finding material (usually documents) of an unstructured nature (usually text) that satisfies an information need, from inside a large collection.

عربي

الـ ir يعني إنك تدور جوه كوم ضخم من النصوص غير المنظمة وتجيب اللي يحقق احتياجك من المعلومة، مش أي حاجة وخلاص

data, information, knowledge

level meaning example
data bare facts, no context a phone number
information data in context a phone book
knowledge information you can act on knowing this number belongs to a client you call every week

ir vs databases

database ir
data structured, fixed format unstructured text
answer one right answer ("how much did you make last year") no single right answer ("documents about hippos in a zoo")

converting all news, emails and web pages into tables is too hard at scale, so ir searches the text directly.

عربي

في الداتابيز الإجابة صح أو غلط، لكن في الـ ir الإجابة بتتقاس بمدى مناسبتها للمستخدم، وده معنى الـ relevance

relevance

relevance = how well an answer fits your need. it depends on the user, time, place, group and context, so it is subjective. everything in ir is about getting it right.

a system is judged by relevance, coverage, recency, speed, availability, usability, query syntax, and time to satisfy the request.

how a system works

user's need -> query text -> parse query ----+
                                             v
collection -> pre-process -> index ----> rank or match -> results
                                             |
                          query reformulation (loop)

ir is iterative: search, read the results, rephrase, search again.

عربي

الـ ir عملية متكررة: بتبحث، تشوف النتايج، تعدل السؤال، وتبحث تاني

quick summary

  • ir = unstructured text + an information need + relevance as the judge
  • unlike databases, there is no single correct answer
  • the loop: need → query → match/rank → reformulate
عربي

الخلاصة: الـ ir بيدور في نصوص غير منظمة، والمعيار هو الـ relevance مش الصح والغلط، والبحث بيتكرر لحد ما المستخدم يوصل للي عايزه

part 2 - boolean retrieval

the naive way: grep

scan every document for every query. fine for small data, hopeless for big data (named after the unix grep).

term-document incidence matrix

question: which plays contain brutus and caesar and not calpurnia? record in advance, for each play, which words it contains. entry (t, d) = 1 if play d contains term t.

antony & cleopatra julius caesar the tempest hamlet othello macbeth
antony 1 1 0 0 0 1
brutus 1 1 0 1 0 0
caesar 1 1 0 1 1 1
calpurnia 0 1 0 0 0 0
cleopatra 1 0 0 0 0 0
mercy 1 0 1 1 1 1
worser 1 0 1 1 1 0

treat each row as a bit vector and apply the operators:

brutus           110100
caesar           110111
not calpurnia    101111      (calpurnia = 010000)
and of all       100100  ->  antony & cleopatra, hamlet

why it doesn't scale: 1 million docs and 500,000 distinct terms give half a trillion cells, but at most about a billion are 1s. the matrix is almost all zeros, so we store only the 1s, which is exactly an inverted index.

عربي

المصفوفة فيها أصفار كتير جدا، فبدل ما نخزن كل الخانات بنخزن بس الأماكن اللي فيها 1، وده هو الـ inverted index

vocabulary

term meaning
boolean model queries are expressions with and, or, not; a doc matches or it doesn't
document whatever unit you index (a play, an email, a page)
collection / corpus all the documents you search
information need vs query the need is the topic in the user's head; the query is what they type

precision, recall, accuracy

relevant non-relevant
retrieved a b
not retrieved c d
  • precision = a / (a+b): of what i returned, how much is useful
  • recall = a / (a+c): of everything useful, how much did i find
  • accuracy = (a+d) / (a+b+c+d): misleading for ir, because d is gigantic. if 10 docs in a million are relevant and the system returns nothing, accuracy is 99.999% and the system is useless
  • f1 = 2pr / (p+r) merges precision and recall into one number
عربي

الـ precision: اللي رجعته كام منه صح. الـ recall: من كل الصح الموجود كام لقيت. والـ accuracy مش مفيدة هنا لأن عدد الوثائق غير المهمة ضخم جدا

the inverted index

two parts:

  • dictionary (vocabulary): the terms, kept in memory
  • postings: for each term, the sorted list of docids containing it, kept on disk
brutus    -> 1 2 4 11 31 45 173 174
caesar    -> 1 2 4 5 6 16 57 132
calpurnia -> 2 31 54 101

building it

  1. collect documents, giving each a unique docid (1, 2, 3 ...)
  2. tokenize into tokens
  3. normalize tokens into terms (friends → friend)
  4. build the index: make (term, docid) pairs, sort by term then docid, merge repeats, split into dictionary and postings, and store the document frequency (df, number of docs containing the term)

example: doc 1 = i did enact julius caesar: i was killed i' the capitol; brutus killed me. and doc 2 = so let it be with caesar. the noble brutus hath told you caesar was ambitious:

term df postings term df postings
ambitious 1 2 julius 1 1
be 1 2 killed 1 1
brutus 2 1, 2 let 1 2
capitol 1 1 me 1 1
caesar 2 1, 2 noble 1 2
did 1 1 so 1 2
enact 1 1 the 2 1, 2
hath 1 2 told 1 2
i 1 1 you 1 2
i' 1 1 was 2 1, 2
it 1 2 with 1 2

df speeds up query processing and later weights terms in ranked retrieval. postings can also hold term frequency and positions.

عربي

بنعمل أزواج (كلمة، رقم الوثيقة)، نرتبها أبجديا، نشيل التكرار، وبعدين نفصل القاموس عن قوائم الـ postings

processing brutus and calpurnia

look up each term, fetch its postings, intersect:

brutus    -> 1, 2, 4, 11, 31, 45, 173, 174
calpurnia -> 2, 31, 54, 101
result    -> 2, 31

two pointers over two sorted lists, always advance the smaller one:

intersect(p1, p2)
  answer = empty
  while p1 != nil and p2 != nil
    if docid(p1) == docid(p2)
      add(answer, docid(p1)); p1 = next(p1); p2 = next(p2)
    else if docid(p1) < docid(p2)
      p1 = next(p1)
    else
      p2 = next(p2)
  return answer

cost for lists of length x and y is o(x + y), since each pointer only moves forward. that is why postings must be sorted.

for a and b and c, intersect smallest df first: the result can never be bigger than the smallest list, so later steps are cheaper.

عربي

بنمشي على القائمتين مع بعض: لو الرقمين متساويين نسجله، وإلا نحرك المؤشر الأصغر. عشان كده لازم القوائم تكون مرتبة

boolean vs ranked retrieval

boolean ranked
match exact, yes or no score per doc
query boolean expression, needs skill free text
result size feast or famine: thousands or zero top-k best

extended boolean adds proximity, wildcards and similar operators. boolean was the main commercial tool for about 3 decades and survives in email search, library catalogs, mac spotlight and westlaw (legal search since 1975, ranking added 1992, most of its 700,000 users still use boolean).

exercises solved

ex 1.1 docs: (1) new home sales top forecasts (2) home sales rise in july (3) increase in home sales in july (4) july new home sales rise

term postings term postings
forecasts 1 new 1, 4
home 1, 2, 3, 4 rise 2, 4
in 2, 3 sales 1, 2, 3, 4
increase 3 top 1
july 2, 3, 4

ex 1.2 / 1.3 docs: (1) breakthrough drug for schizophrenia (2) new schizophrenia drug (3) new approach for treatment of schizophrenia (4) new hopes for schizophrenia patients

  • incidence matrix rows (docs 1-4): breakthrough 1000, drug 1100, for 1011, schizophrenia 1111, new 0111, approach 0010, treatment 0010, of 0010, hopes 0001, patients 0001
  • schizophrenia and drug → schizophrenia = {1,2,3,4}, drug = {1,2} → docs 1, 2
  • for and not (drug or approach) → for = {1,3,4}; drug or approach = {1,2,3}; so {1,3,4} minus {1,2,3} = doc 4

quick summary

  • incidence matrix = correct but huge and sparse → inverted index = dictionary + sorted postings
  • build: tokenize, normalize, sort (term, docid), group, store df
  • and = intersect two sorted lists in o(x+y); start with the shortest list
  • precision = a/(a+b), recall = a/(a+c), accuracy is useless for ir
  • boolean = exact match, no ranking; ranked = scores and top-k
عربي

الخلاصة: الـ inverted index هو قاموس + قوائم مرتبة، الـ and معناه intersect بتكلفة خطية، وبنبدأ بأقصر قائمة. وفي التقييم بنستخدم precision و recall مش accuracy

part 3 - terms, tokens, normalization and faster postings

the pipeline

documents -> tokenizer -> tokens -> linguistic modules -> terms -> indexer -> inverted index
"friends, romans, countrymen"  friends romans countrymen   friend roman countryman

parsing a document

first decide the format (pdf, word, html), the language and the character set (cp1252, utf-8). these are classification problems, usually solved with heuristics or libraries. one index can hold many languages, and one document can mix them (a french email with a german pdf).

what is a document? a grain-size choice: a file, one email inside an mbox file, an email with 5 attachments, or a group of files (a ppt, or latex split across html pages).

tokenization

a token is an instance of a sequence of characters. "friends, romans and countrymen" → friends, romans, countrymen. the hard part is deciding what counts as one token:

problem examples dilemma
apostrophes finland's capital finland + s, finlands, or finland's?
hyphens hewlett-packard, state-of-the-art, lower-case split or keep? asking users to type hyphens helps
multiword names san francisco one token or two?
numbers, dates 3/20/91, 20/3/91, 55 b.c., b-52, (800) 234-2333 embedded spaces; useful for error codes and stack traces (n-grams help); metadata is indexed separately

language issues:

  • french: l'ensemble → l, l', le? it should match un ensemble (google failed until at least 2003)
  • german: compounds are not split (lebensversicherungsgesellschaftsangestellter = life insurance company employee); a compound splitter gives about 15% improvement
  • chinese, japanese: no spaces between words, so tokenization is not unique; japanese also mixes katakana, hiragana, kanji and romaji
  • arabic, hebrew: right to left, but numbers go left to right; letters connect and change shape. in unicode the stored form is simple even though the display is complex
عربي

الـ tokenization يعني تقطيع النص لوحدات. المشكلة إن اللغات مختلفة: الفرنسي بيستخدم الأبوستروف، الألماني بيلزق كلمات، والصيني ما فيهوش مسافات. في العربي الكتابة من اليمين لليسار والأرقام من اليسار لليمين

arabic search in practice (extra, standard): drop diacritics (tashkeel), unify alef forms (أ إ آ → ا), map ى → ي and ة → ه, remove tatweel (ـ), and use a light stemmer for prefixes like ال and suffixes like ات / ون.

normalization to terms

a term is a normalized word type, an entry in the dictionary. normalize the indexed text and the query in exactly the same way, or they will never meet.

  • delete periods: u.s.a., usa → usa
  • delete hyphens: anti-discriminatory → antidiscriminatory
  • accents and umlauts: résumé ~ resume, tübingen ~ tuebingen ~ tubingen. rule: ask how your users actually type; they often skip accents, so de-accenting usually wins
  • dates: 7月30日 ~ 7/30
  • normalization depends on language (is mit the german word or the university?), so it is tied to language detection
  • case folding: lowercase everything. exceptions exist (general motors, fed the central bank vs fed the verb, sail the lab vs the verb) but users type lowercase anyway. google example (fixed in 2011): c.a.t. returned lolcats before caterpillar

asymmetric expansion is the alternative to equivalence classes: the query expands depending on what was typed. more powerful, less efficient.

user types system searches
window window, windows
windows windows, windows (capital w), window
windows (capital w) windows (capital w) only

synonyms: car = automobile, color = colour, handled either at index time (index under car-automobile) or at query time (expand the query). spelling mistakes are handled by soundex and spell correction (part 4).

عربي

الـ normalization يعني نوحد الأشكال المختلفة للكلمة (حروف كبيرة وصغيرة، نقط، شرطات، تشكيل) عشان الكلمة في الوثيقة والكلمة في الاستعلام يبقوا شكل واحد

stop words

a stop list removes the most common words (the, a, and, to, be): they carry little meaning, and the top 30 words make about 30% of all postings. but modern systems mostly keep them:

  • compression makes their space cost tiny, and query optimization makes the time cost small
  • you need them for phrases (king of denmark), titles (let it be, to be or not to be) and relational queries (flights to london)

lemmatization vs stemming

lemmatization stemming
idea proper reduction to the dictionary headword crude chopping of affixes
examples am, are, is → be; car, cars, car's → car automate, automatic, automation → automat
sentence the boy's cars are different colors → the boy car be different color compressed and compression are both accepted as equivalent to compress → compress and compress are both accept as equival to compress

porter's algorithm, the most common english stemmer: 5 phases applied in order; inside a phase, the rule matching the longest suffix wins.

rule example
sses → ss caresses → caress
ies → i ponies → poni
ss → ss caress → caress
s → (nothing) cats → cat
ational → ate, tional → tion
(m>1) ement → (nothing) replacement → replac, but cement stays cement

the measure m roughly counts syllables, so a rule fires only when the word is long enough for the ending to be a real suffix. other stemmers: lovins (single pass, about 250 rules), paice/husk, snowball.

does it help? english: mixed, recall goes up for some queries but precision drops for others (operative in dentistry → oper). spanish, german, finnish: clearly useful (about 30% gain for finnish). full lemmatization gives at most modest retrieval gains. all of this is language-specific, often application-specific, and added as plug-ins.

عربي

الـ stemming بيقص اللواحق بشكل خشن (compressed و compression يبقوا compress)، فبيرفع الـ recall بس ممكن يوطي الـ precision. أما الـ lemmatization فبيرجع الكلمة لأصلها في القاموس بشكل صحيح (are و is يبقوا be)

skip pointers (faster and)

the basic merge costs o(m + n). if the index doesn't change too fast, add skip pointers at indexing time to jump over postings that cannot match.

brutus:  2 -> 4 -> 8 -> 41 -> 48 -> 64 -> 128       skips: 2→41, 41→128
caesar:  1 -> 2 -> 3 -> 8 -> 11 -> 17 -> 21 -> 31    skips: 1→11, 11→31

after matching 8 we compare 41 and 11. 11 is smaller, so try its skip: the rule is follow a skip only if its target is ≤ the other pointer's value. 31 ≤ 41, so jump 11 → 31 and skip 17 and 21 for free.

in the algorithm (figure 2.10), when docid(p1) < docid(p2) you check hasskip(p1) and docid(skip(p1)) <= docid(p2), keep skipping while true, otherwise step with next; same for p2. second example: brutus 2 4 8 16 19 23 28 43 (skips 2→16, 16→28, 28→72) against caesar ... 8 41 51 ...; at 16 vs 41, skip(16) = 28 ≤ 41 so jump (19 and 23 are avoided); skip(28) = 72 > 41, stop.

rules of thumb:

  • skips exist only on original postings lists; intermediate results have none (hasskip() is false)
  • they help and, not or
  • where to put them: more skips = short jumps that often succeed but many comparisons; fewer skips = few comparisons but long jumps that rarely succeed. standard heuristic: √l evenly spaced skips for a list of length l (moffat and zobel 1996). it ignores query distribution and is harder when the index updates often
  • on modern hardware it helps only if the index is in memory; reading a bigger list from disk can cost more than it saves (bahle et al. 2002)
عربي

الـ skip pointers هي قفزات جاهزة جوه الـ postings بتخليك تتخطى أرقام مستحيل تكون في النتيجة. بتفيد الـ and بس، والعدد المثالي تقريبا الجذر التربيعي لطول القائمة

phrase queries

users want "stanford university" as a phrase, so "the inventor stanford ovshinsky never went to university" must not match. about 10% of web queries are phrase queries, and many more are implicit (person names).

1. biword index: every pair of consecutive terms becomes a dictionary term. friends romans countrymen → friends romans, romans countrymen. two-word phrases become a simple lookup. weaknesses: longer phrases need an and of biwords, which can give false positives (stanford university and university palo and palo alto), and the dictionary explodes.

2. positional index: for each term and doc, store the positions: term: doc: <pos, pos...>; doc: <...>.

ismailia:   <1: 1,5,9>   <4: 4,8,10,12,15>
university: <1: 4,8,13>

query "university ismailia": only doc 1 has both words. check ismailia at position of university + 1: university at 4 → ismailia at 5 ✓; at 8 → 9 ✓; at 13 → 14 ✗. doc 1 matches. "ismailia university" matches nothing. longer phrases check +1, +2, ... from the first word.

it also supports proximity: gates /k microsoft = within k words, either side (k = 1 means adjacent). cost: a positional index is typically 2 to 4 times bigger.

عربي

الـ positional index بيخزن مكان كل كلمة جوه الوثيقة، فنعرف إن الكلمتين جنب بعض وبالترتيب. ثمنه إن الفهرس بيكبر من ضعفين لأربعة أضعاف

ex 2.10 gates: 1:⟨3⟩; 2:⟨6⟩; 3:⟨2,17⟩; 4:⟨1⟩ · microsoft: 1:⟨1⟩; 2:⟨1,21⟩; 3:⟨3⟩; 5:⟨16,22,51⟩

  • gates /2 microsoft: doc 1 (3 vs 1, distance 2 ✓), doc 2 (distances 5 and 15 ✗), doc 3 (2 vs 3, distance 1 ✓) → {1, 3}
  • smallest distances: doc 3 = 1, doc 1 = 2, doc 2 = 5, so the answer changes in three ranges: k = 1 → {3}; k = 2, 3, 4 → {1, 3}; k ≥ 5 → {1, 2, 3}

quick summary

  • pipeline: parse → tokenize → normalize (case, accents, periods, hyphens) → index
  • stop words are usually kept; stemming helps recall but can hurt precision, strongest for morphologically rich languages
  • skip pointers: √l spacing, and only, original lists only
  • phrases: biword index (simple, false positives) or positional index (exact, supports /k, bigger)
عربي

الخلاصة: قبل الفهرسة نقطع النص ونوحد الكلمات، وغالبا بنحتفظ بالـ stop words عشان العبارات. للـ and السريع نستخدم skip pointers، وللعبارات نستخدم positional index

part 4 - dictionaries and tolerant retrieval

"tolerant" means the search still works when the query is partial or misspelled.

dictionary data structures

the dictionary stores the vocabulary, df and pointers to postings. a naive version is an array of structs: char[20] (20 bytes) + df (4/8 bytes) + postings pointer (4/8 bytes). two questions: how to store it compactly, and how to look up fast.

hashtable tree
lookup o(1) o(log m), needs a balanced tree
good at fastest exact match prefix search (all terms starting with hyp)
bad at no variants (judgment / judgement), no prefix search, rehash everything when the vocabulary grows slower; rebalancing binary trees is expensive
  • binary tree: root splits a-m / n-z, then a-hu / hy-m, n-sh / si-z
  • b-tree: each internal node has between a and b children (for example [2,4]); this fixes the rebalancing problem and is the usual choice
  • trees need an ordering of characters, which we have

wildcard queries

people use * when: they are unsure of a spelling; they know several spellings (color/colour); they want stemming-like variants without knowing if the engine stems (judicia* catches judicial, judiciary); or they are unsure of a foreign word (universit* stuttgart). * means any string, possibly empty.

  • trailing mon*: easy in a b-tree, take the range mon ≤ w < moo
  • leading *mon: keep a second b-tree of reversed terms, search nom* as the range nom ≤ w < non
  • both ends pro*cent: get pro* from the normal tree and *cent from the reversed tree, intersect the two term sets (works, but costly)

after getting the matching terms you still look up each one's postings, so se*ate and fil*er becomes a large or followed by and; a query like *a*e*i*o*u* is brutal. if a search box encourages wildcards, people will use them.

permuterm index

rotate so the * always ends up at the end. add a marker $ at the end of the word and index every rotation. for hello: hello$, ello$h, llo$he, lo$hel, o$hell, $hello.

query look up
x x$
x* $x*
*x x$*
*x* x*
x*y y$x*
x*y*z z$x*, then filter the results for y

example: hel*o → x = hel, y = o → look up o$hel* → finds hello. cost: the lexicon becomes about 4 times bigger (empirical, english).

عربي

الـ permuterm بيدور الكلمة بكل الطرق الممكنة مع علامة $ عشان أي نجمة تتحول لآخر الكلمة ونستخدم b-tree عادي. عيبه إن القاموس بيكبر حوالي 4 مرات

k-gram (bigram) index

list all k-grams (sequences of k characters) of every term, with $ marking word boundaries. for april is the cruelest month the bigrams are $a ap pr ri il l$ $i is s$ $t th he e$ $c cr ru ue el le es st t$ $m mo on nt h$. keep a second inverted index from each bigram to the dictionary terms containing it (not documents):

$m -> mace, madden, ...
mo -> among, amortize, ...
on -> along, among, ...

mon* becomes $m and mo and on. that also returns moon (it has all three), so post-filter the terms against the original pattern, then look up the survivors in the normal index. smaller and faster than permuterm, but every surviving term still costs a boolean query.

عربي

الـ k-gram index بيفهرس أجزاء الكلمة (حرفين أو ثلاثة) ويقول أنهي كلمات فيها الجزء ده. بنجيب الكلمات المرشحة بـ and ثم نفلترها على النمط الأصلي (مثلا moon بتظهر مع mon* ولازم تتشال)

spelling correction

two uses: correcting the documents being indexed (especially ocr text, with confusions like rn/m, and keyboard-neighbor typos) and correcting queries (our focus, e.g. alanis morisett → either search the right spelling or show "did you mean ...?"). two flavors:

  • isolated word: each word alone; misses real-word typos (from → form)
  • context sensitive: uses neighbors; i flew form heathrow → from

it needs a lexicon of correct words: a standard dictionary, an industry-specific list, or the indexed corpus itself (names, acronyms, but also its typos). then return the lexicon words closest to the query, using edit distance, weighted edit distance or n-gram overlap.

edit distance

the minimum number of operations (insert, delete, replace, optionally transpose) to turn one string into another: dof → dog = 1; cat → act = 2 (1 with transposition); cat → dog = 3. computed with dynamic programming, where d[i][j] is the distance between the first i chars of s1 and first j of s2:

d[i][0] = i        d[0][j] = j
d[i][j] = min( d[i-1][j-1] + (0 if s1[i] == s2[j] else 1),   # match / replace
               d[i-1][j] + 1,                                 # delete
               d[i][j-1] + 1 )                                # insert

cat → act:

      ""  a  c  t
""     0  1  2  3
c      1  1  1  2
a      2  1  2  2
t      3  2  2  2      -> bottom right = 2

weighted edit distance gives each operation a cost depending on the characters, to model ocr and keyboard errors (m mistyped as n is likelier than as q, so m→n costs less). it needs a weight matrix and a modified dp.

عربي

الـ edit distance هو أقل عدد عمليات (إضافة، حذف، استبدال) نحول بيها كلمة لكلمة تانية، وبنحسبه بجدول dynamic programming. والـ weighted بيخلي العملية الأرجح (زي m بدل n) أرخص

using it: generate all strings within a set distance (e.g. 2), intersect with the correct words, show them as suggestions (or search all of them, which is slow, or auto-pick the single likeliest, which saves a round trip but takes power from the user). comparing the query with every dictionary term is too slow, so first cut the candidates with n-gram overlap.

n-gram overlap and jaccard

split the query and the lexicon terms into n-grams, use the n-gram index (the same one as wildcards) to fetch terms sharing n-grams with the query, and threshold on how many match. to normalize, use the jaccard coefficient:

jc(x, y) = |x ∩ y| / |x ∪ y|

it is 1 for identical sets, 0 for disjoint, always in [0, 1], and the sets may have different sizes. example with trigrams: november = nov ove vem emb mbe ber; december = dec ece cem emb mbe ber. 3 grams overlap, so jc = 3 / (6 + 6 − 3) = 3/9 ≈ 0.33, below a threshold like 0.8, so no match.

with bigrams, query lord = lo, or, rd, keeping words that match 2 of 3:

lo -> alone, lore, sloth
or -> border, lore, morbid
rd -> ardent, border, card

lore (lo + or) and border (or + rd) survive. the usual postings merge counts matches and can be adapted to compute jaccard.

عربي

الـ jaccard بيقيس التشابه بين مجموعتين: عدد المشترك مقسوم على عدد كل العناصر. في november و december المشترك 3 من 9 يعني 0.33 فمش متشابهين كفاية

context-sensitive correction

for flew form heathrow no doc matches the phrase, so suggest flew from heathrow.

  • take the close dictionary terms for each word (weighted edit distance) and try phrases with one word fixed at a time: flew from heathrow, fled form heathrow, flea form heathrow; suggest the one with the most hits (hit-based correction)
  • exercise: 7 alternatives for flew, 19 for form, 3 for heathrow. one word at a time: 7 + 19 + 3 = 29 phrases; every combination would be 7 × 19 × 3 = 399. the slide's scheme is the first, but check which one your instructor expects
  • alternative: split into biwords, keep biwords that need only one term corrected, enumerate only phrases built from common biwords

choosing what to show: the alternative with the most hits, query-log analysis, or a probabilistic ranking:

argmax over corrections of  p(correction | query)
  = argmax  p(query | correction) * p(correction)
              noisy channel          language model

soundex

a family of heuristics that expand a query into phonetic equivalents; language specific, mainly for names (chebyshev ~ tchebycheff). invented for the us census in 1918. idea: turn every indexed token and every query term into a 4-character code, and index and search the codes.

  1. keep the first letter
  2. replace a e i o u h w y with 0
  3. replace the rest with digits: b f p v → 1; c g j k q s x z → 2; d t → 3; l → 4; m n → 5; r → 6
  4. collapse consecutive duplicate digits (55 → 5)
  5. remove all zeros
  6. pad with zeros and keep 4 positions: letter + 3 digits

the first letter stays a letter only. zeros are removed after collapsing, so two same-code letters separated by a vowel are both kept (b-a-b → 101 → 11).

herman  -> h 0 6 5 0 5     -> h655
hermann -> h 0 6 5 0 5 5   -> collapse 55 -> h655    (same code)
robert  -> r 0 1 0 6 3     -> r163
rupert  -> r 0 1 0 6 3     -> r163      (collide)

(codes are written lowercase here; the slides write them uppercase, e.g. h655.)

how useful? not very for ir. fine for high-recall tasks (interpol) but biased toward names of certain nationalities; zobel and dart (1996) show other phonetic algorithms work much better. it is still the classic one in most databases.

عربي

الـ soundex بيحول الاسم لكود من 4 رموز (حرف + 3 أرقام) حسب نطقه، فالأسماء المتشابهة صوتيا زي robert و rupert بتاخد نفس الكود. مفيد للأسماء بس مش قوي في الـ ir

everything together

the engine now has a positional index with skip pointers, a wildcard index (permuterm or k-gram), spelling correction and soundex, so it can answer:

(spell(moriset) /3 toron*to) or soundex(chaikofski)

meaning: a spell-corrected moriset within 3 words of any term matching toron*to, or any name that sounds like chaikofski. a query parser splits it into sub-queries and sends each to the right index.

design questions from the final exercise: does stemming happen before the soundex index? what about the n-gram indexes? a reasonable view: n-grams and soundex work on raw or lightly normalized forms, because stemming distorts spelling and sound; the main term index can use stemming.

quick summary

  • dictionary: hash = fast exact lookup; tree/b-tree = prefix search
  • wildcards: trailing → b-tree range; leading → reversed b-tree; middle → permuterm (4× space) or k-gram index (+ post-filter)
  • spelling: edit distance (dp) + n-gram overlap (jaccard) to shortlist; context via one-word-at-a-time and hits; ranking by noisy channel
  • soundex: first letter + 3 digits, phonetic, for names, weak for ir
